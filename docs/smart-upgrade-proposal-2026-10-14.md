**版本基线**：v2.9.0 ｜ **日期**：2026-10-14 ｜ **定位**：决策参考（值不值得做 / 先做什么）

**约束前提**（按你的选择）：

2. 不新增第三方依赖，先做「规则与工程增强」；

## 0. 一页结论

| # | 结论 | 说明 |
|---|---|---|
| 1 | 「不智能」的根源不是缺 AI | 是缺三件**工程派智能**：存量查重、可编辑规则、内容索引。Hazel / DropIt / czkawka / Everything 这些十年前就成熟的工具证明：不用大模型也能很「聪明」。 |
| 2 | 第一优先级 = 重复文件治理（M1） | 你点名的痛点，也是本仓库历史事故的高发区（§1.2）。技术上全部件都已具备：哈希=标准库、缩略图管线=现成、撤销=现成，**零新增依赖**。 |
| 3 | 推荐顺序 | **M1 重复治理 → M2 规则引擎 → M3 全文索引搜索 → M4 学习与建议**。每个模块主体独立可用、做完随时可停。 |
| 4 | 本期明确不做 | 云 API、本地大模型、OCR、语义/向量搜索、无人值守的自动删除。全部列入「长期可选」（附录 C），不占本期工作量。 |
| 5 | 规模与估算 | 单模块 1~2 个专注日（M3 约 2~3 日），四模块合计约 5~8 个专注日；测试沿用现有 154 例基线与 offscreen 回归方式。 |

## 1. 现状诊断：为什么「不智能」

### 1.1 七个「不智能」点（逐条对照代码）

| # | 能力 | 现状（代码依据） | 用户感受 |
|---|---|---|---|
| 1 | 分类 | 只看扩展名（`organizer.classify` + 硬编码 `CATEGORY_RULES`） | 「它不知道 .pdf 里是什么」 |
| 2 | 搜索 | 文件名子串 + 拼音，**每次查询全库遍历**（`search_storage`，已后台化但未索引化） | 「想不起文件名就搜不到；搜不了内容」 |
| 3 | 查重 | **完全没有**。整理时的同名合并（`merge_directory`）只防「再次搬入产生新副本」 | 「重复文件没人管」← 本次首要痛点 |
| 4 | 兜底 | 「其他」格子没有出口、没有归因 | 「越堆越多，没人提醒」 |
| 5 | 规则 | 不可编辑（想按「讲义」这类名字特征分，做不到） | 「规则是写死的」 |
| 6 | 学习 | 不留「意图」痕迹：`handle_drop` 只写移动历史，不记录「为什么拖到这一类格子」，无法沉淀成规则 | 「每次都要手动拖一遍」 |
| 7 | 建议 | 无洞察、无提醒（没有 stale/大文件/重复报告） | 「它从不主动说话」 |

### 1.2 聚焦：重复副本问题（本次痛点专章）

历史证据链（全部来自本仓库 CHANGELOG / PROJECT.md）：

- **v2.6**：收纳库「文件夹」分类出现 **14 份内容一致的 jifang 副本**（各约 77MB，合计 ≈ 1.08GB），逐份校验后人工清理；
- **v2.7.0**：自动整理时序缺陷导致同名文件夹反复再现 → 副本成堆（fish.jokerx.top / jifang / markdown 各 7 份）；
- **v2.7.2**：只读文件跨盘移动失败 → **43 项编号副本，人工回收约 11.1GB**；
- **现状**：`merge_directory` 解决了「整理时不再叠新副本」，但**存量重复从未被系统性扫描过**；「其他」格子、映射文件夹、自定义格子之间也没有任何查重。

> 结论：重复治理是这个项目最贵的一课（累计人工清理 >12GB），也是从「收纳箱」到「管理员」感知提升最强的一步。以上数字均可核对：`CHANGELOG.md` / `PROJECT.md` 的 v2.6、v2.7.1、v2.7.2 条目。

## 2. 对标：成熟项目怎么做「智能」（互联网调研摘要）

### 2.1 五条路线与代表项目

| 路线 | 代表项目 | 成熟度 | 一句话概括 |
|---|---|---|---|
| 规则引擎 | Hazel（macOS）、DropIt（Win/开源）、File Juggler、Belvedere | 10 年+ | 「条件 → 动作」；用户可编辑、有优先级、可干跑 |
| 查重治理 | czkawka（Rust/开源）、dupeGuru（Python/开源）、Easy Duplicate Finder、Gemini 2 | 10 年+ | 大小分组 → 预哈希 → 全哈希；预览确认；默认回收站 |
| 即时搜索 | Everything（MFT/USN 文件名秒搜）、AnyTXT / Orange（全文内容）、DocFetcher / Recoll | 10 年+ | 预建索引 + 增量更新；查询毫秒级 |
| 文档智能 | Paperless-ngx（46.6k★，自托管） | 成熟 | OCR + 全文检索 + 用「你已有的标注」训练自动标签 |
| AI 新派 | Sparkle（Every）、Sortio、AI File Sorter（开源） | 2024~2026 | 说人话 / 读内容直接整理；预览 → 执行 → 撤销；可接本地模型 |

### 2.2 最值得抄的 8 个具体设计

1. **预哈希 + 预哈希缓存**（czkawka）：先对文件首尾各 4KB 做快速哈希排除非重复项，再对候选做完整哈希；缓存让**重扫只算新增/变更文件**——「第一次慢、以后秒出」的关键机制。
2. **参考目录保护 + 选择预设**（czkawka）：备份/参考目录永不可被删除；「保留最旧 / 最新 / 最短路径」一键选区。
3. **大小分组 → 候选才读内容**（dupeGuru）：不读没有希望的组；删除默认走回收站；误报可「移出结果集」。
4. **规则模型全貌**（DropIt）：通配符/正则 + 大小/日期/属性/**文件内容**过滤；优先级星标；处理前先「汇报将要做什么」再确认。
5. **规则语义**（Hazel）：每个文件**只应用首个命中的规则**（干净、可预期）；any/all 组合；「预览规则」；可停用/暂停；用「忽略」动作显式排除。
6. **索引化搜索**（Everything / AnyTXT）：Everything 靠 NTFS 的 MFT/USN 日志实现文件名秒搜（<2MB 体积、完全离线）；AnyTXT 用内置文档解析引擎做内容秒搜（Office/WPS/PDF/电子书）。两者组合是国内效率用户的经典方案。
7. **国内用户预期基线**（腾讯桌面整理 / DeskGo）：一键整理（按类型 + 时间分组）、自定义格子、文件夹映射（你已有）、**全盘搜索「秒出」**、**「最近文档」格子**、格子收起。说明大众认知里的「智能」就是：整理准、找得快、有「最近」视图。
8. **AI 产品的收敛设计**（Sortio / Paperless-ngx / AI File Sorter）：即使有 AI，也全部落在——**预览后再执行、一键撤销、持久 undo、从用户已做的 review 决策学习**；Sortio 甚至把自然语言直接编译成**确定性规则**来跑日常（AI 只负责生成规则，规则负责执行）。Paperless-ngx 的自动标签同样是「用你已标注的样本训练」，而非凭空智能。

### 2.3 结论：先走「零依赖工程路线」是理性选择

- 成熟工具的全部高价值设计（上表 1~7）都不需要大模型；
- 你的库当前规模（768 文件 / 1.55GB）用确定性算法就能从容完成（目标：全量 ≤1 分钟、重扫秒级），AI 的边际收益低、维护成本高；
- AI 路线的产品形态（预览/撤销/学习）与上述设计高度重合。本期把骨架做好，未来接 AI 是「换引擎」，不是「推倒重来」（见附录 C）。

## 3. 推荐方案：四个模块

> 总原则（沿用项目红线）：本地离线、无轮询（事件驱动）、只建议不自动删、全部动作可撤销、offscreen 测试全覆盖。
> **「零新增依赖」口径**：不新增任何第三方包；继续使用既有依赖（PySide6、pypinyin）。核心查重/规则/索引逻辑均为纯标准库（hashlib、sqlite3、zipfile、fnmatch、re）。

### M1 重复文件治理（P0，直击痛点）

**能力目标**：一键找出收纳库（可含映射格子）内的完全重复文件与相似图片；安全、可撤销地回收空间。

#### （1）算法：三层漏斗

| 层 | 方法 | 说明 |
|---|---|---|
| ① 大小分组 | `os.stat` 收集 (path, size, mtime_ns) | 单成员组直接排除，绝大部分文件止步于此 |
| ② 预哈希 | 首尾各 4KB 的快速哈希（对齐 czkawka 口径） | 同尺寸里筛掉「头尾已不同」的 |
| ③ 完整哈希 | 全文件 SHA-256（stdlib `hashlib`） | 仅对候选执行；结论 = 内容 100% 一致 |

**缓存**：SQLite（stdlib `sqlite3`）落盘 `%APPDATA%\MyDeskOrganizer\dedupe.db`，键 `{path, size, mtime_ns, prehash, fullhash}`；size+mtime 未变直接复用；每次扫描顺带清理失效路径的孤儿条目。首次全量后，之后每次扫描只读新增/变更文件。

#### （2）相似图片（可选开关，默认关）

- 复用现有 QImage 管线：解码 → 9×8 灰度 → **dHash**（64 位）→ 汉明距离 ≤ 阈值（默认 5）分组；
- 明确声明「相似 ≠ 重复」，结果默认只做人工确认（与 czkawka 官方提醒一致）；
- 设比较上限（如 ≤5000 张）避免 dupeGuru 式 N² 比较失控；
- 相似组**默认不参与一键选择**（只浏览、手动勾选），「保留最新/最旧」预设仅作用于完全重复组。

#### （3）安全设计（四道闸）

| 闸 | 机制 |
|---|---|
| 1 | 扫描只读：任何删除都必须人工确认（对齐现有 `confirmOrganize` 文化） |
| 2 | 执行 = 移入暂存区 `收纳库\_重复暂存\<日期>\`，批量写 MoveRecord → **一键撤销**可用 |
| 3 | 暂存区复查后可「彻底清理」→ 批量送回收站（复用 `move_to_recycle_bin`） |
| 4 | 参考目录保护：被标记目录（如桌面、某分类文件夹）**只参与比对、其文件永不被列为删除项**；典型用法=把桌面设为参考，只在收纳库内清理副本 |

`_重复暂存` 纳入全局忽略名单：搜索、格子展示、后续扫描/索引一律跳过（避免把暂存文件当重复项二次计算）。

#### （4）交互（面板新增「重复文件」页）

- 顶部：范围选择（默认整个收纳库，含所有格子文件夹；可选勾选「把映射格子一并扫描」）、相似图片开关 + 阈值、「开始扫描」（后台线程 + 进度）；
- 结果：分组卡片——组内文件数、单文件大小、**可回收空间**（= 每组 (文件数−1) × 单文件大小 合计）；行内显示路径/时间/图标（图片显示缩略图，可并排对比）；
- 一键预设：「保留最新 / 保留最旧 / 保留路径最短」，再手动微调；
- 底部：「移到暂存区（X 项 / Y MB）」与「取消」。

#### （5）验收指标

| 指标 | 目标 |
|---|---|
| 首次全量（当前 768 文件 / 1.55GB） | ≤ 1 分钟（后台，不卡界面） |
| 无变化重扫 | ≤ 2 秒（全走缓存） |
| 新增 10 个文件后的增量扫描 | ≤ 2 秒 |
| 完全重复误报 | ≈ 0（SHA-256 碰撞概率可忽略） |
| 相似图片（可选） | 只浏览不代选、阈值可调；结果供人工核对 |
| 回溯 | 「移到暂存区」可一键撤销（写 MoveRecord）；送回收站后走回收站恢复 |

**工作量**：新增 `dedupe.py`（哈希/缓存/分组为纯逻辑，图片指纹复用既有 Qt 能力）+ 面板页 + SQLite 缓存；+15~25 个测试；1~2 个专注日。

### M2 可编辑规则引擎（P1）

**能力目标**：把「扩展名硬编码」升级为「用户规则 + 内置规则」双层；规则可编辑、可测试、可停用。

- **规则模型**（存 settings.json，复用原子写）：

```json
{
  "name": "数学讲义自动进文档",
  "enabled": true,
  "priority": 10,
  "match": {
    "ext": [".pdf"],
    "name_glob": "*讲义*",
    "size_min": 10485760,
    "content_contains": null
  },
  "action": { "move_to": "文档", "rename": null }
}
```

- **匹配语义**（借 Hazel）：**首个命中生效**，两层顺序：用户规则（按列表顺序 / 可选 `priority` 字段）→ 内置扩展名规则（`classify` 兜底）；UI 分两段展示，顺序对用户始终可见。
- **干跑**（借 DropIt）：「测试规则」按钮列出当前会命中的文件，所见即所得；整理前预览（现有）自动包含规则命中项。
- **集成点**：`_iter_candidates` / `organize_desktop` / `preview_organize` 的分类决定统一改走 `rules.resolve()`；自动整理与手动整理天然一致。
- **内容关键词条件**（`content_contains`）：可选扩展，**M3 索引就绪后启用**；M2 本体不依赖 M3。（例：「内容含『报销』的 pdf → 自动进『文档』」）
- **UI**：面板「规则」区：列表（名称 / 条件摘要 / 开关 / 排序 / 编辑 / 删除）+「新建规则」+「测试」。
- **验收**：能用规则实现 3 个真实场景（名字含「讲义」→ 自定义格子；>100MB 压缩包 → 单独分流；覆盖内置扩展名规则）；停用/删除后行为即刻回退内置规则；非法规则不崩（容错）。

**工作量**：新增 `rules.py` + 规则编辑对话框；+15 个测试；1~2 个专注日。

### M3 全文索引 + 即时搜索（P1.5）

**能力目标**：搜索从「每次全库遍历文件名」升级为「索引内毫秒级查询」，并首次支持**文件内容检索**。

- **引擎**：SQLite FTS5（**已在本机验证可用**：Python 3.9.13 自带 sqlite3 支持 FTS5，无需新依赖）；索引库放 `%APPDATA%\MyDeskOrganizer\index.db`（不动收纳库）。
- **内容抽取矩阵**（全部标准库）：

| 类型 | 方式 |
|---|---|
| txt / md / csv / log / json / 代码 | 直接读（编码容错 + 截断限长） |
| docx / xlsx / pptx | `zipfile` 解包 + XML 文本节点（标准库） |
| html / htm | 去标签 |
| pdf | **本期仅索引文件名**（正文抽取需第三方库，列为可选扩展） |
| 其他 | 仅文件名 |

- **拼音**：索引期写入全拼/首字母列（现有 pypinyin 能力迁移进索引），搜索行为与现在一致。
- **增量**：复用现有文件监听事件 → 防抖 → 后台重索引；首次构建后台分批 + 进度（不阻塞）。
- **隐私开关**：`indexContent`（默认开）可关闭——只索引文件名；索引全部本地，符合「严禁上传」红线。
- **降级与重建**：FTS5 不可用时回退现有 `search_storage` 全遍历；索引缺失=后台重建、损坏（完整性校验失败）=删库重建，重建期间同样回退全遍历（不崩、不阻塞）。
- **体验**：面板搜索 + 桌面搜索条接口不动，底层换引擎；新增「命中片段」显示（哪句话里命中了）。
- **验收**：768 文件库任意查询 < 50ms；搜 docx/txt 里的内容词能命中；删掉索引文件后自动重建不崩。

**工作量**：新增 `index_store.py` + 抽取器 + SearchService 接线；+15~20 个测试；2~3 个专注日。

### M4 学习型规则 + 主动建议（P2）

**能力目标**：让「你教它」变成它「记住」；让工具第一次学会「主动说话」。

- **学习**（借 Paperless-ngx「从已有标注学习」的极简版）：
  - 记录「纠正事件」：拖入/粘贴的 (扩展名、名字关键词、来源、目标格子) → `%APPDATA%\MyDeskOrganizer\intents.jsonl`；
  - 同类事件 ≥3 次且无规则覆盖 → 面板出现建议：「是否记住：**.docx**（名字含『周测』）→ 进『文档』？[采纳/忽略]」；
  - 采纳 = 自动生成 M2 规则（无需手写条件）；忽略写入 dismissed 名单，不再骚扰。
- **洞察**（只建议，不执行）：
  - 重复回收报告（来自 M1）、大文件 Top 10（索引现成）、≥180 天未修改的文档、「其他」格子增长与建议；
  - 彩蛋「**最近收纳**」格子：直接从历史记录生成「最近 20 条收纳」视图（腾讯桌面整理「最近文档」的降级版：基于收纳历史而非全盘打开记录，成本极低）。
- **验收**：拖拽 3 次同类文件后出现建议；忽略后不再出现；每条建议可展开说明「为什么」。

**工作量**：新增 `insights.py` + 面板「建议」区；+10 个测试；1 个专注日。

## 5. 非目标与风险

**本期明确不做（及原因）**：

| 项 | 原因 |
|---|---|
| 云 API（含任何上传） | 隐私红线；`.gitignore` 已声明「严禁上传」 |
| 本地大模型 / OCR / 语义搜索 | 违反「零新增依赖」；接口已为将来预留（附录 C） |
| 无人值守的自动删除 | 一切删除必须人工确认；「送回收站」同样是人工点下的动作 |
| MFT/USN 原生索引（Everything 路线） | 需 ctypes 深水区与管理员权限，收益边际 |

**风险与对策**：

| 风险 | 对策 |
|---|---|
| 误判导致误删 | 完全重复 = 全哈希（≈0 误报）；相似图 = 只建议；执行三重防护：人工确认 → 暂存区（可撤销）→ 回收站（可恢复） |
| 扫描/索引拖慢电脑 | 后台线程 + 分批限速 + 事件驱动增量；游戏模式全暂停（沿用现有开关） |
| 索引/缓存损坏 | 均可删档重建；索引重建期间回退全遍历搜索（不崩、不阻塞） |
| 规则冲突 | 首个命中生效（Hazel 语义）+ 干跑预览 + 操作日志 |
| 暂存区占用磁盘 | 面板显示暂存区体积；清理提醒；「彻底清理」入口显眼 |

## 6. 结论

1. 「变智能」的正确顺序是：**先查重（M1）→ 再规则（M2）→ 再索引（M3）→ 后学习（M4）**。每一步都直接对应你已付出的代价（12GB 人工清理、写死的分类、「找不到」），而不是为了功能而功能。
2. 四件事全部零新增依赖、全本地；合计约 5~8 个专注日（一到两周）可全部落地。
3. AI（本地小模型 / 语义搜索 / 自然语言指令）不必现在做；做完 M1~M4 后，附录 C 的接口会让它变成「可选引擎」而非「重写产品」。

## 附录 B：关键技术速览（给实现者的 trust-but-verify 清单）

- **预哈希漏斗**：首尾各 4KB（对齐 czkawka）；缓存键 `(path, size, mtime_ns)`；mtime 用 `st_mtime_ns` 防秒级截断误判（本仓库 v2.7.2 已有同类教训）。
- **dHash**：9×8 灰度 → 相邻像素比较 → 64 位指纹；汉明距离阈值经验值 3~10（默认 5）；只用于「建议人工确认」，不参与自动删除。
- **FTS5**：外部内容表或普通表 + 触发器均可；写入为「先删后插」保证幂等；损坏检测（`PRAGMA integrity_check`）失败即回退。
- **性能预算**：完全重复全哈希的真实开销 = 仅「同尺寸 + 同头尾」文件的完整读取；当前库最坏 1.55GB 顺序读，实际远小于此。
